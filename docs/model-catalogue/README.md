## Source and acquisition decision

The [existing Landing evidence](../pilot-inputs/manufacturer-inputs.md) and [pilot decision](../pilot-inputs/pilot-decision.md) were inspected first. The provider's current product page still advertises 14 × 41 ft, 520 ft² interior area and 9 ft ceilings. The 9 ft ceiling is not building height. The [Click homepage](https://www.clickmodular.com/home) states near-term service only on the Sunshine Coast, so Victoria availability is **excluded by the provider's current general statement**, subject to later confirmation. This makes Landing a research comparator, not a purchasable Victoria option.

Two [aux box Model 240](https://www.auxbox.ca/model-240) and [Model 300](https://www.auxbox.ca/model-300) pages provide explicit exterior dimensions, a manufacturer-labelled footprint and overall exterior height. Their pages say they deliver anywhere in North America and use crane placement. That is a provider delivery claim, not a confirmed Victoria installation commitment. Their height datum and roof high point are undefined; the selector leaves **Building height** blank. Model 240's 24 ft 1 in length is represented as an approximate decimal-foot value in the existing `Quantity` contract; the original text stays alongside it. The component renders the normalized value as `7.3406` m while the full conversion remains in the source baseline. Confirm a controlled drawing before any precise placement use.

The inspected provider pages did not document an authorized catalogue API or structured licensed download. The earlier [DASH resource lead](https://www.acceleratedhousing.ca/) does not identify an authorized model API, so no endpoint or integration is invented. A manual transcription of three provider pages is pinned in [`app/model_catalogue/catalogue.json`](../../app/model_catalogue/catalogue.json) and the identical frontend copy in [`frontend/src/model_catalogue/catalogue.json`](../../frontend/src/model_catalogue/catalogue.json), generated by [`build_snapshot.py`](../../app/model_catalogue/build_snapshot.py). The copy allows the existing container frontend build to use only `frontend/src`; `--check` fails if either artifact differs from the authored transcription. The Python loader rejects malformed versions, inconsistent units, missing known quantities, duplicate IDs and detached source references. Runtime does not fetch provider sites. A missing snapshot is an error to the loader; a UI caller can pass `catalogue={null}` for explicit manual mode.

Source pages were fetched on 2026-09-25 with bounded requests and their byte SHA-256 values recorded. Only limited factual transcriptions and hashes are committed. The previously captured Landing page/drawing bytes are retained privately per the pilot packet; aux page bytes and the Click homepage were **not retained** because redistribution rights have not been established. Their `capture_gap` status records that limit. Upstream controlled model revision is unknown for all three. A page hash and capture date identify the observed version without claiming a design revision. No provider was contacted.

## Consumer contract for SR-41 / #89

`ModelInputs` is standalone and controlled. It never calls an API, submits a form, changes navigation, evaluates rules or publishes data. The parent owns the draft and must invalidate any previous summary on **every** `onChange`, including model switching, identity edits and a height-reference change. `changeSequence` increments for each such action. Model switching clears the previous model's overrides; an override of the selected model retains its original source measurement in `fields[field].baseline` and marks `origin: 'user'`. Manual mode has no source baseline and remains `unreviewed`. If a model revision or snapshot changes in a future release, restore only by explicit selection against the pinned version; do not silently upgrade a stored selection.

```tsx
import { ModelInputs } from './model_catalogue/ModelInputs'
import { assessmentValues, emptySelection } from './model_catalogue/model'
import './model_catalogue/model-inputs.css' // import from the app entry, as assessment CSS is

const [selection, setSelection] = useState(emptySelection)
<ModelInputs value={selection} onChange={next => {
  setSelection(next)
  // Dispatch assessment edits for width/depth/height/area using assessmentValues(next).
  // Clear submitted/result state on every call, even if mapped values remain blank.
}} />
const mapped = assessmentValues(selection)
// { width: '4.2672', depth: '12.4968', height: '', area: '48.3095808' }
```

The example values are for The Landing at this snapshot. `assessmentValues` returns blank for invalid decimal input or building height with unknown reference. The user may assert a foundation-datum-to-roof-high-point reference, but that statement and value remain unreviewed. It must not be converted to regulatory grade height. Existing assessment `width`, `depth`, `height`, `area` fields have the corresponding physical definitions. The parent should retain the complete `Selection` beside its plain strings so that model ID, snapshot ID, field baselines, origins, and measurement reference are available in the summary. The existing assessment reducer will need an integration action or coordinated change to carry that object and clear `submitted`; SR-41 owns it. `App.tsx`, shared assessment model and global CSS were intentionally left to their owners.

The selected Model 300 consumer payload has `modelId: 'aux-300'`, `modelRevision: null`, `snapshotId: 'sr-40.2026-09-25.provider-pages.v1'`, source width `3.0480` m, source depth `9.1440` m, source living area `20.99608704` m², blank height, `heightReference: 'unknown'`, and `reviewStatus: 'unreviewed'`. No regulatory value is included. The source's separate exterior height remains in `measurements` for inspection.

## Verification and remaining work

### Published-dimensions correction (September 28, 2026)

The Model 240 page was rechecked at **The Specs > Dimensions** after a user reported
that its height appeared missing. It still lists 24 ft 1 in long, 10 ft wide and
10 ft 3 in high: approximately 7.34 × 3.05 × 3.12 m. This is a live corroboration
of the existing transcription, not a replacement snapshot or accepted design revision.

The original catalogue commit `0e30487` (September 25) already stored
`advertised_overall_height = 3.124200 m` with its original 10 ft 3 in value and
page/section citation. That same commit mapped the editable height field only to
`roof_height`, because the exterior-height statement did not specify the foundation
datum or roof measurement point. **This was a presentation omission, not failed
extraction.** The UI put the useful height in cautionary prose and an expanded list
while leaving the prominently labelled "Building height" input blank. The placement
workspace showed only width and depth. Tests preserved the mapping restriction but
did not check that the published height remained prominent.

The correction shows a shared **Published exterior dimensions** panel in model
entry, preparation summary and the occupied-lot workspace. It uses the existing
source quantities, original units, rounded metric display, source locator/link,
capture date and review status. The provider-review text carries these dimensions
as source facts, separately from edited inputs. Following user feedback, the separate
input is labelled **Height (m)** with an information button that reveals the technical
term **roof height from foundation datum** and its definition. The button supports
click/tap and keyboard activation, exposes its expanded state to assistive technology,
and opens inline help rather than relying on hover. A short measurement hint stays
visible; the reference selector asks **How was this height measured?**. The 2D workspace explicitly states that
it does not check height. Missing exterior heights remain missing; ceilings are
not used as substitutes. No catalogue bytes, evaluation semantics or release change.

The regression extends the existing ModelInputs behavior test through preparation
and its copyable summary: the source's 10.25 ft × 0.3048 = 3.1242 m must be visible
(rounded to 3.12 m) while the assessment height remains unresolved. The quality
agreement now explicitly checks visibility as well as uncertainty propagation.
Installed foundation/grade relationships and rule-specific height references remain
separate acquisition questions; they do not prevent showing published dimensions.

The same presentation pattern now covers **Width**, **Length**, **Height** and
**Interior floor area**, with units and accessible information buttons. Shared
physical-measurement copy keeps model entry, placement controls, validation and
the preparation summary consistent. Original terms remain in the help and review
export; the stored `depth`, quantity bases and assessment mapping are unchanged.
The visual/quality guides and AGENTS.md establish this as the default for future UI
work, with jurisdiction-specific definitions requiring their own source/revision.

Ordinary metric input displays and summaries now round lengths to at most two
decimal places and areas to one, to nearest. Model 240's 3.048 m width therefore
shows 3.05 m, and its 13.56384384 m² interior area shows 13.6 m². Focusing a field
reveals its editable full value; focus/blur alone does not change it. Source baseline
details and technical exports retain full values. Evaluations continue to use the
stored values, and small nonzero overlaps or shortfalls are shown with explicit
bounds instead of becoming zero. This is a display policy, not an accuracy claim
or an upward planning allowance.
