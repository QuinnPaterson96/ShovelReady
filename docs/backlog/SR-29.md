# SR-29: Prepare reproducible virtual-user runs with isolated local execution

Status: Planned; starts after SR-27 contract integration (September 24, 2026)
GitHub issue: https://github.com/QuinnPaterson96/ShovelReady/issues/53
Milestone: M1 support
Dependencies: SR-27; complete integration verification with SR-28 fixtures
Related: SR-20, SR-21, SR-26; see [evaluation plan](virtual-qa-plan.md)

## Outcome

Make selecting a case, preparing its browser environment and collecting a participant
result repeatable, without creating an unattended agent orchestration service.

## Acceptance criteria

- [ ] Provide a local CLI with dry-run/plan, prepare and result-ingest/finalize stages.
  Select fixed baseline IDs or seeded samples within explicit category/split filters.
  Record exact selected IDs and revisions, stable ordering, seed, algorithm version and
  run mode. Test repeatable draws and exclusion of reserved/ineligible groups. Sampling
  is reproducible; no deterministic model-output claim is made.
- [ ] Require explicit owned output/scratch locations and app/data inputs. Reuse the
  existing demo/database helpers and loopback port handling for a clean pinned build.
  Use fresh isolated data only when the scenario requires a DB. Protect the user's
  existing preview/default DB and validate ownership before any cleanup.
- [ ] Materialize SR-28 variants only in owned disposable copies, with exact fixture and
  variant identities. Preserve baseline bytes and the clean-build identity guarantee;
  document the narrow approach selected with SR-28. No production endpoint, global
  setting, accepted-data update or silent application monkeypatch is allowed.
- [ ] Emit only the participant brief, URL and necessary browser operating constraints
  for handoff. Keep facilitator rubrics/fault metadata out of participant context and
  served files. Require a fresh context and disclose isolation limits. File-based manual
  dispatch is an acceptable initial adapter; report it as manual, not automatic dispatch.
  Do not reverse-engineer unsupported Codex interfaces or require a new paid API.
- [ ] Save actual participant note, action/evidence pointers and tool/environment failures.
  Preserve existing run records; refuse accidental overwrite. Record screenshots as
  files only through supported export facilities, or retain a precise tool-history
  reference and state that the run lacks a portable screenshot bundle.
- [ ] Enforce planning/session ceilings and no silent retry. The initial policy is one
  participant at a time, at most ten minutes or 60 actions per session. A manual adapter
  supplies explicit facilitator stop instructions and records actual enforcement limits.
  Timeouts, cancellations and invalid environments are visible outcomes, not passes.
- [ ] Stop only owned processes and verify cleanup on success/failure. Offline tests cover
  selection, budget/retry bookkeeping, result validation, artifact preservation and
  ownership/refusal paths. Perform one actual preparation/cleanup smoke check using
  disposable resources; no live participant is required by this tooling ticket.

## Ownership and delivery

Own `scripts/virtual_qa/runner.py`, focused runner tests and
`docs/usability/virtual-qa/runner.md`. Coordinate shared contracts with SR-27 and fixture
materialization with SR-28; avoid unrelated edits to existing database/demo helpers.
Any necessary shared helper change must be declared in the PR. No scheduler, queues,
cloud infrastructure, automatic GitHub issue creation or live-model CI. Deliver the
tooling and actual verification evidence; SR-31 owns the participant pilot.
