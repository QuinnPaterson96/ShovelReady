# Next steps after the computed draft integration

September 24, 2026. This is a proposed sequence grounded in merged PRs #68/#69 and
[their integration evidence](integration-wave-seven.md), not newly dispatched work.

## Immediate objective

Make one actual design/site/placement case useful for investigation, with one or two
independently reviewed checks and explicit unresolved remainder. This is the next
learning milestone within M1, whose full target remains about three real fixtures and
5-8 supported checks. A small complete evidence chain is more informative now than
increasing the number of synthetic examples. An honest investigation result is valid;
there is no requirement to find a positive fit.

The software now computes, stores and displays a detailed draft report. The main
missing input is an attributed, reproducible real case. The existing
[reviewer action list](pilot-inputs/reviewer-actions.md) already names the artifacts
needed; do not create another general discovery survey or repeat provisional annotation
as if it were independent acceptance.

## Two evidence tracks can proceed together

| Track | Owner/input needed | Smallest useful return | Existing tickets |
|---|---|---|---|
| Rule/source subset | Project owner identifies a technical reviewer and resolves authorized retention/access | One selected current pathway and 1-2 clauses with exact pinned evidence, applicable definitions/dependencies, legal-date limitations, review rationale and unresolved remainder | SR-01/05/06 |
| Design/site/placement subset | Design supplier and site-fact supplier, with attributed review | One controlled design configuration plus one site and supplied placement; only the actual measurements required by those checks, with units, measurement basis, provenance and revision | SR-01/05/06/09 |

Review is about the stated checks, not a demand to certify an entire project. Do not
silently add requirements for professional certification beyond the existing evidence
scope, but an agent-authored annotation cannot become independent review. Record who
supplied and who reviewed each item, what they checked, and any disagreement. No
manufacturer, municipality, reviewer or customer outreach is sent by this plan.

Victoria remains the leading candidate. The Landing remains conditional on controlled
drawings/measurements. If that model cannot supply usable inputs, compare another
documented small design before changing municipality. The historical Stannard packet
is useful evidence of conditions/revision problems; its permit history is not a shortcut
to current applicability or a verified fit for The Landing.

## Proposed next implementation assignments

1. **Real-case intake and diagnostic replay (SR-05/06/10/13).** Once one usable packet
   is supplied, add the smallest file-based mapping into current source/input/fact/
   binding contracts and the existing evaluator. Keep reviewed source-derived rules
   intact and every unresolved condition visible. No auto-acceptance, invented
   measurements or fake Evidence objects. Verify source hashes/rights disposition and
   exact revisions, and preserve a failed/incomplete attempt as a diagnostic. Reuse the
   new draft storage; the current synthetic-only HTTP aliases must not be repurposed
   to expose private material. A separate explicitly scoped read boundary follows
   actual data-sharing requirements. Exit: reproducible real diagnostic plus a finite
   list of unsupported semantics and missing inputs, not necessarily a pass.
2. **Case-driven semantics and publication (SR-10/11).** Use observed failures from
   that packet to decide whether the existing direct-measurement core suffices. If a
   condition, override or definition blocks the check, specify and test that exact
   behavior; do not delete the condition or introduce a universal rule language.
   Then implement the smallest reviewed release manifest/projection and atomic
   activation path, with source/input/schema/evaluator identity, explicit compatibility
   and coverage. Exercise two releases, an explained correction, failed publication,
   concurrent activation and restoration of the prior release. Synthetic fault tests
   can verify mechanics, but acceptance and current-law claims need actual evidence.
3. **Accepted path and extraction benchmark (SR-07/12/13).** Connect the reviewed
   release to evidence inspection and an offline source-to-result regression. Preserve
   the separation between source text, normalized rules and projected checks. With a
   reviewed corpus subset, manual baseline and explicit live-run budget, run the original
   extraction prompt and measure omissions, consequential errors and actual review/
   correction effort before tuning. The one real case alone is not a held-out benchmark;
   retain development/holdout separation and unsupported-case reporting.
4. **Protected demo and first user workflow (SR-14/15/16).** After the real chain and
   packaging are reproducible, choose a project-specific hosting account/budget, deploy
   the existing single image with one database and authorized artifact storage, and
   verify explicit migration, rollback and backup recovery. First measure whether a
   person can identify the checked scope, evidence and next missing fact. The broader
   20-30-enquiry commercial pilot follows that usable prototype.

Task 1 depends on the usable evidence subset. Task 2 depends on its demonstrated
semantics and review boundary; publication mechanics and read-only presentation can
then be split after that interface is frozen. The extraction benchmark can run alongside
publication implementation once the reviewed corpus and budget exist. No additional
worktrees are started by this plan, and no parent is closed by the synthetic demo.

## Stop/reconsider criteria

- If a bounded real check still cannot be assembled, identify the precise obstacle:
  unavailable controlled design/site measurements, unresolved source authority/rights,
  missing review, or unsupported semantics. Change the failing input/pathway based on
  evidence; additional frontend work does not resolve it.
- If a domain reviewer cannot explain a useful narrow rule/measurement mapping, revise
  supported scope before writing conditional evaluation code.
- If producing and maintaining the first reviewed check needs substantial manual work,
  record that effort rather than assuming LLM extraction will remove it. This is an
  early test of the data-economics thesis.
- If a user cannot act on the resulting evidence/missing-fact list, improve that bounded
  workflow before extending geography, mappings, integrations or APIs.

Keep the current on-demand QA tooling available for confirmed UI regressions. SR-30
human calibration and commercial/provider research remain separate follow-ups; they
are not reasons to delay the real-case evidence work.
