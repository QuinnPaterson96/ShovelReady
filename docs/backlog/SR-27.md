# SR-27: Define virtual-user case, run and finding records

Status: Ready for bounded implementation (September 24, 2026)
GitHub issue: https://github.com/QuinnPaterson96/ShovelReady/issues/51
Milestone: M1 support
Dependencies: Review SR-26 report evidence; preparation need not wait for its merge
Related: SR-06, SR-13, SR-26; see [evaluation plan](virtual-qa-plan.md)

## Outcome

Give the case library, runner and grader a small shared format so results can be
reproduced and findings can be adjudicated without confusing software defects with
agent errors, unresolved source facts or hypotheses about human usability.

## Acceptance criteria

- [ ] Define typed, versioned file records for case definition, run record and finding.
  Keep these in QA tooling, separate from regulatory data contracts; reuse existing
  identity types only where meanings agree. Reject unsupported versions and malformed
  records without interpreting embedded text or expressions as code.
- [ ] Cases contain stable ID/revision, category, synthetic/observational/reviewed status,
  fixture/source references, expected behaviors with evidence and reviewer status,
  explicit unknowns, supported task mode and group/split assignment. Distinguish observed
  UI facts, authored software expectations and independently reviewed legal expectations.
  Unreviewed legal claims cannot become scored truth. Record rubric disagreements.
- [ ] Separate a participant-facing brief from a facilitator-only rubric and seeded-fault
  metadata. Require each scored item to identify its browser-observable basis or explicit
  task instruction. Do not penalize failure to know hidden case facts. Rubrics are fixed
  before dispatch; later corrections receive new revisions, retaining the original grade.
- [ ] Runs identify application and frontend commits, case/fixture/rubric revisions,
  data identity kind and revision (observation, synthetic fixture or accepted release),
  participant prompt and available model/tool settings, selected IDs/seed, mode, timings,
  budget, final note, evidence pointers and completion/timeout/blocked status. Unknown
  metadata stays null with a reason. Every retry is a linked new attempt.
- [ ] Findings carry affected run/check, claim, supporting/contradicting evidence, severity,
  reproduction status, adjudication status/reviewer/date/rationale and any linked issue.
  Categories cover app defect, agent omission/error, false alarm, source/data gap,
  environment/tool failure and usability hypothesis. Support unresolved/disputed findings.
- [ ] Document fresh-participant boundaries, task versus detection mode, fixed/seeded
  samples, holdout grouping and criteria for escalating confirmed findings into tickets.
  A second model's agreement alone is not authoritative adjudication.
- [ ] Provide a compact sample based on the SR-26 report with actual omissions and no
  invented app bug; record that it is a report-derived example, not a new participant run.
  Validate positive records and meaningful rejection/identity/unknown-state cases offline.

## Ownership and delivery

Own `scripts/virtual_qa/contracts.py`, package initialization, focused contract tests,
and `docs/usability/virtual-qa/protocol.md`. Coordinate exact exported interfaces before
SR-28/SR-29/SR-30 branch. Keep ordinary Python/Pydantic and repository dependencies;
no new database, agent framework or runtime HTTP API. Propose any CI wiring to the
integrator. Follow AGENTS.md and the PR template; deliver implementation/evidence in a
PR without merging. This ticket defines the protocol; it launches no participant.
