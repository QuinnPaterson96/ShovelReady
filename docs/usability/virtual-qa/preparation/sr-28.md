## Minimal proposed SR-29 handshake (not a schema or implemented API)

1. SR-27 supplies merged exported case/run/finding types, version, validation entry
   points, identity/hash conventions, mode/category/group values, rubric evidence and
   reviewer fields, and representation of synthetic versus observation data. SR-28 maps
   this note to that contract rather than introducing parallel records now.
2. SR-28 supplies case/brief/rubric references plus reviewed finite replacement assets
   or exact patches scoped to the three display targets above. Each recipe declares
   baseline commit, allowed repository paths, before/after SHA-256 hashes and expected
   difference. No executable expressions from record text. Confirm whether hashes use
   Git blob bytes or checkout bytes and pin newline handling; table hashes are explicitly
   checkout bytes. Build artifact hashes are recorded after building, not invented now.
3. SR-29 owns materialization into an explicitly owned disposable checkout. Proposed
   approach: apply the allowlisted exact change there, verify all other tracked bytes,
   and create a local derived commit with the required personal identity. Retain baseline
   commit, recipe digest, derived commit/tree and artifact hashes separately. Refuse
   mismatched preimages or unexpected changes. Do not bypass `scripts/demo.py`'s clean
   checkout checks or label a modified build as the baseline. Clean controls use baseline
   bytes; record clean/fault build identity differences as execution metadata.
4. SR-29 returns the actual loopback URL, app/frontend identity, data kind/revision,
   verified materialized digests, owned resource handles and preparation status. Synthetic
   runs should need no DB: agree a clean pinned static-build path, since the existing
   demo launcher requires explicit observation DB configuration. VIC-080 uses existing
   owned DB helpers with new scratch configuration/start/migrate/seed and records the
   returned revision; mismatch with the pinned case stops preparation for reconciliation.
5. Serve only application assets. Brief handoff contains URL and necessary browser
   constraints; recipes, grading expectations and fault labels remain outside served
   files and participant context. No fault switch enters the ordinary app bundle.
   SR-29 owns process cleanup and preserved run output; SR-28 owns fixture/difference
   validation and facilitator browser review. An unavailable materialization path is
   blocked preparation, not a silent mock API or fallback to an existing preview.
