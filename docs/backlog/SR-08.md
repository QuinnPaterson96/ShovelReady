# SR-08: Persist rule revisions, review history, and dataset metadata

Status: Complete - immutable PostgreSQL persistence merged in PR #26 (wave 1 integration: 2026-09-24)
Milestone: M1: Technical proof
Dependencies: SR-02, SR-04

## Outcome

Store accepted knowledge and ingestion history without losing provenance or overwriting old interpretations.

## Scope

Use SQLAlchemy migrations and one PostgreSQL database, relational identities plus validated JSONB as needed.

## Acceptance criteria

- [x] Migrations apply to empty disposable database and upgrade the previous supported fixture schema.
- [x] Store source/design/site references, raw-run references, candidates, review decisions, logical rule IDs, immutable revisions, and release metadata.
- [x] Repeat imports do not duplicate accepted revisions; failed transactions leave existing records intact.
- [x] A correction produces a new revision; an older revision remains retrievable with its evidence.
- [x] Ambiguous rule identity changes, including splits/merges, require an explicit mapping decision; startup does not auto-create application tables.

- [x] Persist immutable site-fact and proposed-placement revisions, including manual review provenance. A changed placement or corrected building footprint must not overwrite inputs to an earlier result.

## Out of scope

No full administrative web application or generalized event-sourcing system.

## Verification evidence

Migration and repository tests against disposable PostgreSQL; sample revision history.

## Open decisions and constraints

Initial review can be a CLI/file workflow with reviewer, rationale, and timestamp.
