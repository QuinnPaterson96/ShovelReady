# Model 300 journey analytics decision note

Status: **proposal only**, 2026-10-05. Scope: the stateless, independent Model 300 builder demonstration in [issue #206](https://github.com/QuinnPaterson96/ShovelReady/issues/206). No collection, vendor account, dependency, endpoint, or production configuration is implemented by this note.

## Decision and reason

Use a small, explicit product-event vocabulary to locate *where* visitors stop in the Model 300 journey. If a pilot is authorized, prefer hosted PostHog Product Analytics for ordered funnels with event-property breakdowns, subject to the privacy and activation gate below. Keep request rates, latency, error rates and uptime in operational monitoring. Prometheus is not a visit funnel: its guidance warns against user IDs and other unbounded labels. Do not put session IDs, property IDs, addresses or enquiry details in metrics. [PostHog funnels](https://posthog.com/docs/product-analytics/funnels); [Prometheus instrumentation](https://prometheus.io/docs/practices/instrumentation/); [Prometheus label guidance](https://prometheus.io/docs/practices/naming/).

Hosted PostHog supports sequential funnels, combined event steps, property filters and conversion windows, which fit the paths and retries here. The simpler alternative is Plausible: explicit custom events and goal funnels can show aggregate drop-off, but its funnels are built from configured goals and property-specific steps require property-filtered goals; funnel analysis is currently a Business-plan feature. Plausible may be preferable if only aggregate start-to-handoff rates are needed after a pilot. Neither destination is activated here; choose a region, retention and commercial plan only after the collection decision. Do not build a custom analytics backend without a concrete unmet need. [Plausible custom events](https://plausible.io/docs/custom-event-goals); [Plausible funnel analysis](https://plausible.io/docs/funnel-analysis); [Plausible property-filtered goals](https://plausible.io/docs/custom-props/for-custom-events).

This measures observed browser actions, not visitor intent, site feasibility, qualified leads, or sent enquiries. Interview and observe consenting users to learn *why* they leave. A large apparent drop-off at a step is a prompt for investigation, not proof that the step caused it.

## Current UI and proposed event contract

Use stable `builder_*` names below. Emit only from named transitions, not generic clicks or DOM text. The current source anchors are `frontend/src/App.tsx`, `builder_demo/BuilderDemo.tsx`, `builder_demo/ExampleProperty.tsx`, `site_discovery/SiteDiscovery.tsx`, `manual_site/ManualSiteInput.tsx`, `occupied_lots/OccupiedLots.tsx`, and `ReadableProvenance.tsx`. The table maps existing behavior; it does not claim instrumentation exists.

| Event | Existing action and firing condition | Allowed distinction |
|---|---|---|
| `builder_journey_started` | First entry to Model 300 from Home or navigation in an attempt; once per attempt. Do not fire on each render or return to Home. | `entry=home_cta\|nav\|direct\|mode_reset` |
| `builder_path_selected` | Explicit “Use my own property”, “Try an example property”, selector change, or first live search if the default live mode was never explicitly chosen. The selector also offers `retained`, a separate example workflow. | `path=live\|manual\|example\|retained` |
| `builder_property_confirmed` | Live `SiteDiscovery.confirm()`, retained `SitePreparation` confirmation, or manual “Confirm my site description”. The saved example is **selected**, not a visitor property confirmation. | `path=live\|manual\|retained` |
| `builder_lookup_failed` | A completed lookup with no usable address/parcel observation or a bounded service failure, after showing the fallback. | `failure_category` only |
| `builder_measurement_requested` | Explicit “Measure this placement” in live, retained or manual mode; also the saved example's automatic initial measurement after selection. Fire only once per actual request. | `path`, `request_origin=automatic_example\|button` |
| `builder_measurement_completed` | Current request returns a valid, displayed measurement. A late response for an invalidated revision is ignored. | `path` |
| `builder_measurement_failed` | Current request fails or returns unusable data, after the user-visible failure state. | `failure_category` only |
| `builder_enquiry_ready` | “Mark enquiry ready” transitions the current draft from not ready to ready. A rendered preview is **not** this event. | `path`, `has_current_measurement=true\|false` |
| `builder_copy_requested` / `builder_copy_confirmed` / `builder_copy_failed` | Plain-text enquiry “Copy text” button and clipboard promise result. Keep email-body and technical-evidence copy out of this first funnel, or give them separate fixed `copy_surface` values. | `copy_surface=enquiry` |
| `builder_download_requested` | “Download Markdown enquiry” invokes the browser download. The app cannot establish that the file was saved; no `download_confirmed` event. | none |
| `builder_email_draft_requested` | Valid “Open in default email app” or “Open in Gmail” invokes the URL/open call. It does not establish that an email client opened, a draft was retained, or a message was sent. | `draft_target=default\|gmail`, `body_variant=full\|short_fallback` |
| `builder_state_invalidated` | A confirmed property, current measurement or ready draft becomes stale after a material edit, reset, rejection or mode change. Use for diagnostics, not a funnel success. | `scope=property\|measurement\|enquiry`, `cause=edit\|reset\|mode_change\|reject` |

There is deliberately no `enquiry_sent`, `lead_created`, `qualified_lead`, `approved_site`, or `fit_verified` event. The app creates a local unsent preview and can request a clipboard operation or email draft; it has no delivery acknowledgement. “Copy confirmed” means the browser clipboard promise resolved, not that text was pasted or sent. A download or draft request is an *attempted handoff* only. Existing integration evidence says the actual mail-client draft handoff and browser download delivery still need a smoke test: [enquiry integration](integration-enquiry-journey.md).

## Counting rules

**Unit and boundary.** Report both sessions and attempts; default funnel unit is a journey attempt. One random, opaque visit ID lives in first-party session storage for one browser tab, rotates after 30 minutes of inactivity and on a new tab, and is never derived from IP, address, device or account. A separate random attempt ID begins on first Model 300 entry and on each property-mode change that clears state. Within an attempt, placement edits increment a local revision counter; they do not create a new attempt. Reload clears UI state, so it starts a new attempt even if the tab visit ID survives. Do not join visits across tabs, browsers or days. PostHog's event identity may itself be pseudonymous; the implementation must verify that its SDK does not persist a longer-lived distinct ID than this policy permits. No `identify()`, aliasing, user profiles or cross-visit stitching. [PostHog anonymous versus identified events](https://posthog.com/docs/data/anonymous-vs-identified-events).

**Ordering.** Count the first qualifying occurrence of each step *after* the prior step, within one attempt and 30 minutes from `builder_journey_started`; the later event must have a later request/transition sequence, even when timestamps tie. A retry may create several request/failure events but only one attempt reaches “measurement completed”. A completion must match the latest active request and revision. Once ready is invalidated, a subsequent ready event may occur, but it does not add a second converted attempt. A mode switch closes the old attempt and starts another; a new path is not retrospectively applied to the old attempt. A visit-level view deduplicates attempts by visit ID and reports its own denominator; do not mix it with attempt counts.

**Primary funnel:** `journey_started → path_selected → enquiry_ready → any handoff requested` (`copy_requested` OR `download_requested` OR `email_draft_requested`). Denominator at each rate is the preceding step's eligible attempts; also display the start-denominator conversion. `enquiry_ready` is a deliberate mark, not necessarily required by current UI before copy/download/email, so show handoffs occurring *without* prior ready separately rather than dropping them from all reporting. In the first iteration, do not infer a sent enquiry from this funnel.

**Branch funnels:** for own-property paths (`live`, `manual`, `retained`), `path_selected → property_confirmed → enquiry_ready`; for saved `example`, `path_selected → measurement_requested → measurement_completed → enquiry_ready`. The example is never pooled with real-property confirmation or used as evidence of a live lead. A manual visitor can reach a useful enquiry without measuring: report `property_confirmed → enquiry_ready` independently of the measurement branch. The measurement diagnostic is `measurement_requested → measurement_completed`, with failure categories alongside it and one request-stage denominator per attempt. Report raw request and retry counts separately. Stratify by path and `app_release` before comparing changes; do not sum incompatible UI releases into a trend without annotation.

**Missing events and uncertainty.** Client events can be blocked, lost on navigation, or suppressed by consent and network conditions. Treat missing as *unobserved*, not abandonment. Reconcile a small consented manual walkthrough against observed events and test the vendor payload before interpreting rates. Show numerator/denominator counts, exclusion count and dates, not only percentages. Small samples should be described as directional with no significance claim; avoid ranking paths from a handful of sessions. No individual path reconstruction or contact matching. Human observation remains the next step for causes of friction.

## Strict data allowlist and activation gate

Each custom event may contain only: event name, event time, opaque visit and attempt IDs, local revision integer, `analytics_schema=builder-funnel.v1`, `app_release` (short deploy version/commit), `qa_class=public\|internal\|agent_qa`, and the fixed enum fields named above. `failure_category` is bounded to `no_result`, `unsupported_area`, `service_unavailable`, `timeout`, `invalid_response`, `invalid_input`, `clipboard_unavailable`, or `other`. Categorize locally without exception messages, raw status bodies, query text or provider response. `qa_class` is set from an explicit internal/test environment or test launch flag under operator control, never guessed from IP or user agent. Suppress internal and agent QA before sending when feasible; always filter them from public reports and show excluded counts.

Never send addresses or site descriptions, coordinates, parcel IDs, source identifiers, measurement values, recipient addresses, enquiry text or other free text, full URLs or query strings, raw exceptions, IP-derived location, referrer strings, browser/device fingerprints, or arbitrary event properties. Do not capture form values or technical evidence exports. A vendor may receive network metadata such as IP at ingestion even if it is absent from event properties; pseudonymous IDs and provider access still make this privacy-relevant processing, not anonymous data. Choose and disclose processor, region, purposes, opt-out/consent behavior and retention before activation. Set a short documented raw-event retention target (proposed 90 days, subject to vendor plan and deletion capability), restrict dashboard access, and document deletion handling. Do not assume a vendor default equals this policy. [PostHog privacy controls](https://posthog.com/docs/privacy); [PostHog event-retention API](https://posthog.com/docs/api/events-retention).

If PostHog is chosen, configure explicit named capture only: disable autocapture, automatic pageviews/pageleave, session replay, error autocapture and any SDK feature that adds URLs or DOM/form properties; do not enable identify/person profiles. Guard outbound events with a schema allowlist and inspect the **actual network payload**, including SDK-added properties, before live use. A payload that cannot satisfy the allowlist blocks launch. Do not use session replay or autocapture to explain drop-off. PostHog's product docs describe these as optional capabilities, not privacy guarantees. [PostHog analytics](https://posthog.com/docs/product-analytics/funnels); [PostHog session replay](https://posthog.com/docs/session-replay).

Activation requires a named product owner to approve the question and reporting unit, a privacy/hosting owner to decide disclosure, consent, processor region and retention, and an implementation owner to prove allowlist and QA exclusion on a synthetic browser run. Keep collection off by default until those choices are recorded. Do not create an external analytics account, add billing, or send events under this issue.

## Synthetic example and follow-up ticket

[Synthetic event fixture](product-analytics/synthetic-funnel.csv) uses invented IDs and no property or enquiry content. Under the counting rules above, it contains **6 public visits, 7 public attempts, 1 excluded QA attempt**. The public primary funnel is **7 started → 7 selected a path → 5 marked ready → 4 requested a handoff** (ready-to-handoff: 4/5; start-to-handoff: 4/7). Own-property branch: **5 selected → 4 confirmed → 3 ready**. Saved-example branch: **2 selected → 2 requested measurement → 2 completed → 2 ready**. Measurement diagnostic: **4 attempts requested → 3 completed**; raw requests are 6 because one attempt retries and one example remeasures after an edit. A single enquiry clipboard confirmation is observable; the failed copy, requested download and requested email draft are not sent enquiries. These are arithmetic examples, not product observations.

### Ready-to-implement follow-up: instrument the bounded Model 300 funnel

1. Implement one typed event gateway with the allowlist above and explicit call sites for the existing UI transitions. Preserve request/revision identity so stale completions cannot convert. Emit no event when collection is disabled. Keep the work in the existing frontend; no telemetry endpoint or backend storage is needed for the initial pilot.
2. Add consent/disclosure and a visible opt-out per the privacy decision. Configure the chosen hosted destination with automatic capture and replay off, a session-scoped identity, reviewed region and retention. Prevent external SDK loading before the gate permits collection. Record the exact SDK version and audited configuration.
3. Verify a synthetic browser journey for live lookup success/failure, manual no-measurement readiness, example automatic measurement, retry, edit invalidation, mode reset, clipboard success/failure, download request and both draft targets. Compare ordered attempt counts with the fixture. Inspect vendor-bound requests to prove only allowed keys/values, no URLs/query strings or content, and no events after opt-out. Verify internal and agent QA exclusion, reload/timeout behavior and release splitting.
4. Create only the named funnels and a bounded failure-category view. Show denominators, excluded sessions, missing-event caveat and app release. Observe a few consented humans before treating a drop-off as a usability cause. Verify operational metrics separately, without session labels.

**Acceptance:** the public primary and branch counts match the fixture under the documented unit; every event maps to an observable current transition; the complete outbound payload passes the allowlist; a draft request is never labeled sent; collection stays off until owner decisions are recorded. This ticket implements measurement only. Source review, accepted zoning publication, actual provider enquiry delivery and customer validation remain separate work.
