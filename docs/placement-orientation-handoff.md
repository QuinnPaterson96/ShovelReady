# Initial parcel orientation handoff (#210)

## Implemented

`suggestPlacementOrientation(site)` in `frontend/src/placement_orientation/index.ts` is a pure, deterministic suggestion for one projected-metre parcel exterior. It returns `{status: 'suggested', angle_degrees, long_axis_degrees, aspect_ratio, method}` or an explicit `{status: 'ambiguous' | 'unavailable', reason}`. The caller supplies the existing `Site` parcel and `projected_metre_crs` fields. No coordinates are edited or rounded. The angle is in degrees for the existing placement engine: width is local X, depth (building length) is local Y, and positive rotation is counterclockwise in projected XY. Equivalent rectangle directions normalize to `[-90, 90)`.

The method removes a duplicate closing vertex and consecutive duplicates, checks a finite simple ring, forms a convex hull, and evaluates the enclosing rectangle at each hull edge. It chooses the smallest-area rectangle and aligns local Y to its long axis. Reversing ring order gives the same result. A concave **single exterior** is supported through its hull; this can mask indentations, so the result only suggests orientation. Holes, multipart geometries, malformed/self-intersecting or zero-area rings, and mismatched coordinate systems return `unavailable`. The site contract must genuinely contain metre-based projected coordinates; a misleading CRS label cannot be detected from numbers alone. A best rectangle with aspect ratio below 1.1, or near-minimum rectangles within 1% area that disagree by more than 2° on the long axis, returns `ambiguous`. These are conservative presentation thresholds, not surveying tolerances.

## Integration instructions for the UI owner

- Import `suggestPlacementOrientation` and call it once when initializing a **new** placement for a selected parcel. Apply `angle_degrees` only for `status === 'suggested'`. Use the current editable manual angle as fallback for `ambiguous` or `unavailable`.
- Offer an optional **Align to lot** action that calls the helper on demand and applies a suggested angle only when available. Keep an explanatory status/reason when no suggestion exists. Never recalculate and overwrite a user-edited rotation on rerender, model change, or response arrival.
- Use the existing placement edit/invalidation path when changing the angle, so an old measurement is cleared and a new measurement is required. Keep reset semantics explicit. The helper does not choose a placement centre.
- In visible copy, call this a shape-based initial direction. It does not identify legal frontage, find a feasible position, prove containment or clear space, establish setbacks, or optimize fit. Preserve the parcel source attribution and approximate/unreviewed status already shown by the host.

Independent examples for integration: a 30 m east-west by 10 m rectangle has long axis 0° and suggested building angle -90°; the same rectangle rotated 30° has building angle -60°; a north-south rectangle has 0°. The saved VIC-087 parcel yields approximately **-9.52°** (long axis approximately 80.48°), from its 41.56 m by 6.97 m long edge. Its geometry is an unreviewed City of Victoria observation, so the number is a geometric suggestion only.

## Verification and limits

Starting base: `bd1d345ee719ebc7e229c6d28ed07b6b55fdfc09` (`origin/main` at checkout creation). From `frontend/`, `npm ci`, `node --import tsx --test src/placement_orientation/orientation.test.ts` (4/4), `npm run typecheck`, `npm test` (95/95), and `npm run build` passed. The build reported its existing large-chunk warning. The tests use independently constructed 0°, 30°, 90° and 135° rectangles, reversed and closed rings, the saved parcel, a concave exterior, and unavailable/ambiguous cases. They protect angle convention, stable direction and uncertainty handling; they do not establish survey accuracy or whether any footprint fits. No database, source publication, or live model call is involved.

The helper is not wired into the UI in this PR because the four host UI files are owned by parallel work. Until that integration, demo users still start with the existing angle and cannot invoke Align to lot. The UI owner should implement the initialization/action and one browser journey covering manual rotation persistence and stale-result invalidation. Site identity/source review, roofline and obstruction completeness, legal rule review, accepted publication and real-user comprehension remain separate gates for real evaluation; the corresponding product/research owners must supply that evidence. This helper alone is not an accepted site-fit result.
