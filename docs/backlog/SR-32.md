# SR-32: Persist and serve reproducible draft evaluator runs

Status: Ready for dispatch (2026-09-24)
Milestone: M1 preparation
Parents: SR-10, SR-12, SR-13; does not complete their accepted-data criteria
Dependencies: Existing sr-10.v1 evaluator and SR-08 persistence; no SR-33 dependency
GitHub issue: https://github.com/QuinnPaterson96/ShovelReady/issues/65

## Problem and outcome

The evaluator currently returns a full draft report in Python, but storage accepts a
different release-shaped result and the app cannot inspect an actual evaluator run.
Add an explicit offline evaluate/import command, immutable diagnostic storage, and a
read-only endpoint for a small, pinned synthetic demonstration. This exercises the
software path while the real source/design/site review gates remain open.

## Acceptance criteria

- [ ] Reuse `EvaluationRequest`, `EvaluationReport`, and `evaluate()` without changing
  their `sr-10.v1` / `bounded-scalar.v1` meanings. Persist the full request and computed
  report, including all evidence, diagnostics, alternative, fact and revision identities.
  Do not coerce a draft into SR-04 `EvaluationResult` or invent a release ID.
- [ ] The CLI takes a local request and explicit ShovelReady database configuration,
  validates and evaluates it, and atomically imports an immutable diagnostic record.
  Identical replay is a no-op; changed content at the same identity fails. A supplied
  report is not accepted as proof that the evaluator produced it. No implicit URL
  fetching, schema migration, source acceptance or active pointer is introduced.
- [ ] Add an additive migration and repository support proportional to this one new
  record kind. Preserve existing stored records/readers. Incomplete rule/fact references
  that the evaluator intentionally diagnoses remain representable; do not turn every
  unresolved diagnostic into an import failure or silently manufacture referenced rows.
- [ ] Ship three explicitly invented requests: `synthetic-direct-pass`,
  `synthetic-missing-fact`, and `synthetic-placement-failure`. Author independent
  arithmetic expectations; the displayed reports must come from the real evaluator.
  Runtime code must not import `tests` or reinterpret the old authored preview results.
- [ ] `GET /api/draft-evaluations/{case_id}` returns the existing `EvaluationReport`
  JSON directly. Case IDs are the three aliases above, mapped server-side to exact
  diagnostic identities and pinned request content. No list endpoint is needed.
  `SHOVELREADY_DRAFT_EVALUATIONS_ENABLED=true` explicitly enables this demo; missing or
  false means 503. Unknown case is 404 when enabled; unimported known case is 404;
  invalid/incompatible stored content is 502; unavailable database is 503. Error bodies
  contain a safe `detail`, without raw payloads, paths or credentials.
- [ ] This endpoint serves only the repository-owned synthetic demonstration. Verify
  the request pin and report consistency before returning it. Private CLI inputs,
  arbitrary database records and source files are not exposed through aliases or URL
  parameters. Startup stays free of connections, writes and migrations.
- [ ] Verify isolated PostgreSQL migration/readback, replay/conflict, failed import
  preservation, old-record compatibility, exact report roundtrip and API failure states.
  Include missing facts, wrong/stale identity and failed-placement scope. Preserve all
  existing CI checks and the native Windows database lifecycle check.
- [ ] Document reproducible local import and inspection commands using an explicitly
  owned development database. Tests use the guarded disposable runner. Record the
  difference between synthetic software coverage and the still-missing real evidence.
