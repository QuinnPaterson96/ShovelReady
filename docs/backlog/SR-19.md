# SR-19: Build a fixture-driven investigation preview and rehearse user tasks

Status: Ready, optional parallel work (checkpoint: 2026-09-24)
Milestone: M1: Technical proof preparation
Dependencies: SR-02, provisional SR-04 (both merged)

## Outcome

Find confusing result labels, hidden unknowns and missing evidence before integrating the real evaluator. Prepare a reusable task script for later real-user sessions.

## Scope

Timebox a first pass to one small PR: a local React preview using explicitly synthetic, contract-valid saved results; six goal-based scenarios; and one recorded browser walkthrough. Keep the current health check usable. This is a presentation/rehearsal task, not a second application or an evaluation engine. Use the current frontend and a small fixture adapter; no new agent service, live model integration or cloud deployment.

## Acceptance criteria

- [ ] Clearly label the preview and all examples as synthetic. No real parcel or manufacturer is presented as a successful fit. Keep the fixture adapter separate from the later API boundary.
- [ ] Cover a candidate with scope exclusions, missing roof/grade facts, failure of one supplied placement, outside coverage, an unresolved reference or approval condition, and an older result pinned to its original release after a correction. Use state combinations permitted by the current contracts; document any contract gap rather than inventing an incompatible payload.
- [ ] Show design/site/placement revisions, evaluated scope, check outcomes, units and ratio bases where relevant, rule/source references, source capture versus legal-effective dates and release identity. Do not turn unknowns into green passes, approvals or universal site failures.
- [ ] Validate saved result payloads with existing Python contracts through a focused offline check; do not write a competing TypeScript zoning ontology or use synthetic fixtures as an evaluator oracle. Render source-like content inertly. Preserve keyboard access and text labels in addition to colour.
- [ ] Prepare goal-based tasks for the hypothesized manufacturer qualification coordinator and a technical reviewer. Keep tester instructions separate from the expected-answer rubric. First-pass browser exploration receives only user-visible information, not hidden fixture answers. If the author also rehearses the tasks, disclose that contamination rather than claiming independent validation.
- [ ] Record actual navigation, visible text and reproducible failure evidence against a commit/fixture version. Label each finding as an observed UI defect, a model-generated usability hypothesis or an unverified behavior. Do not invent human hesitation, completion time, satisfaction, demand or accuracy statistics.
- [ ] Add deterministic regression checks for consequential observable defects where appropriate. Ordinary CI uses saved data and deterministic checks; no simulated-user model calls in PR CI.
- [ ] Record what was actually exercised, remaining blockers, and the handoff to SR-12 and SR-16. If browser testing is unavailable, mark the walkthrough unverified. A successful model walkthrough is not evidence that humans understand or want the product.

## Out of scope

No evaluator, database/API implementation, auto-placement, citywide map, persona farm, paid testing service, user outreach, or changes to accepted data. This does not complete SR-12 or SR-16.

## Ownership and dependencies

Own `frontend/` preview components, `docs/usability/` and isolated synthetic preview fixtures/checks. SR-08 owns shared Python dependencies, migrations and `.github/workflows/ci.yml` in the concurrent wave. Use the existing test-discovery locations and dependencies where practical; propose necessary shared changes explicitly. Do not alter `app/contracts` unilaterally. Documentation for this work lives under `docs/usability/` to avoid concurrent README edits.

## Verification evidence

Preview startup/build/typecheck results; contract validation of fixture payloads; versioned scenario script and answer rubric; browser evidence and a short findings ledger with explicit evidence categories.

## Research basis and limits

This is a small rehearsal informed by the role of simulation in study preparation, not adoption of a simulation platform. [UXAgent](https://arxiv.org/abs/2504.09407) frames simulated interaction as a way to refine study design before human testing. [GOV.UK's usability guidance](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing) calls for clear, non-leading tasks and actual or likely users. Subsequent SR-16 sessions must establish human understanding and workflow value.
