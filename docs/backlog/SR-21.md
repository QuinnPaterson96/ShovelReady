## Outcome

A clean merged checkout can launch the current observation demo with one documented command after explicit database preparation. Viewers can distinguish the running application build from its selected spatial data revision.

## Scope and acceptance criteria

- [x] Add a small PowerShell launcher using the current native database workflow and one FastAPI process serving the built frontend. Keep preparation (`start`, `migrate`, `seed`) explicit; ordinary HTTP startup must not migrate, reseed, drop data or select an implicit latest revision.
- [x] Accept a deliberate owned database configuration path and exact spatial revision; load credentials only at use and never echo or commit them. Detect missing configuration, unavailable database/revision and occupied HTTP port with useful errors. Use the existing documented port or an explicit override.
- [x] Resolve paths independently of the caller's working directory. Verify a clean Git checkout, record its commit and build the frontend before launch. Never auto-pull, stash, reset, switch another worktree, or kill/adopt an unrelated process. The actual stable demo checkout is selected/refreshed by the integrator after merge, not created speculatively by this task.
- [x] Expose a minimal versioned nonsecret app identity response and an inspectable UI panel showing application commit/build identity, selected observation revision and explicit no-screening status. Capture identity at launch/build, not by reading a subsequently changed checkout on each request. Report unavailable identity honestly for generic/container starts; preserve existing health behavior and safe startup without database configuration.
- [x] Keep app identity distinct from dataset acceptance. Do not reveal local paths, database URLs, environment dumps or claim an accepted release. Preserve the fictional preview and real-observation separation.
- [x] Exercise the launcher from a clean task commit against a new scratch database, not the user's persistent database. Check visible identity against the actual launched commit and seeded revision, startup failures, and shutdown ownership. No orphan HTTP/database processes after verification; stopping HTTP must not silently stop the persistent database.
- [x] Add focused tests for consequential launcher/identity behavior and run relevant frontend checks/browser verification. Record exact commands, results and unverified behaviors in the updated local-development handoff.

## Ownership and exclusions

Own `scripts/demo.ps1` (or a similarly small launcher), focused launch/identity helpers and tests, `app/main.py` plus a small identity module if needed, relevant frontend identity UI, and `docs/local-development.md`. SR-20 owns CI and lifecycle tests; SR-22 owns AGENTS/PR templates. Do not change persistence, evaluator semantics, investigation payload meaning or shared dependencies speculatively. No cloud hosting, generic process supervisor or background service installation. Launch background verification helpers hidden on Windows.
